深入 WebRTC · 第 2 讲

协商是一台状态机

一句话目标：读完这一讲，你能一眼挑出 SDP 里真正决定「通不通」的那几行，能判断一次改动要不要重新协商，并且明白为什么「手改 SDP」几乎总是错的那一步。

引子：两个人都没说谎

客服坐席 A 和客户 B 通话。音频正常，A 说「我这边有画面」，B 说「我看不到你」。两边都没撒谎，日志也没报错：iceConnectionState 与 connectionState 都是 connected。

把 B 端的 SDP 抓下来，视频那段写着 a=inactive；再看 A 端的 getStats()，inbound-rtp 里视频的 bytesReceived 三分钟没动过。

真相是：A 看到的不是实时画面，而是重新协商前 <video> 里残留的最后一帧。 播放器不会因为远端停发就擦成黑屏，它只是停在那里——一个冻结帧足以让排查方向彻底跑偏。

那个 inactive 来自 A 端点的「关闭摄像头」：transceiver.direction = 'inactive'，再发一次新 offer。这一步是对的。错在重新打开时只把 track.enabled 设回了 true，方向没改回来。

意义不在这个 bug，而在于：SDP 不是描述「我有什么」的配置，是两端刚签下的临时合同。 合同写了 inactive，浏览器就一个字节也不发，无论 track.enabled 是什么。想改合同，只能重签。

这一讲讲三件事：合同长什么样、签字走几步、哪些改动必须重签。

SDP 是一份文本合同

格式原始得有点可爱：纯文本，一行一条，每行 <type>=<value>，type 是一个小写字母。层级只有两层：第一个 m= 之前是会话级，之后是媒体级，媒体级继承并覆盖同名属性。所以 a=ice-ufrag 出现两次不奇怪——会话级那份给整条传输，媒体级那份给单条流。

m= 这一行是位置语言

整份 SDP 信息密度最高的就是 m=，它按位置解析，五个位置各有含义：

位置含义读它时该想到什么
m=标记：下面开始描述一条媒体流它是分界线，不是数据
媒体类型audio / video / applicationapplication 就是 DataChannel
端口这条流的端口offer 里常写 9，因为它不重要；写 0 表示这条流被拒绝
传输协议如 UDP/TLS/RTP/SAVPFTLS 就是 DTLS，SAVPF 是带反馈的 SRTP profile——加密被写死在语法里
载荷类型列表如 111 96 0 8只是号码，要靠 a=rtpmap 翻译成「什么编码、多少采样率」

还有第六个隐含字段：它在整个会话里的次序。在 a=mid 出现之前，两端就是靠第几条 m= 对号入座的。这个历史包袱到 BUNDLE 那节会回来找你。

至于 v= s= t=，几乎永远不用看。o= 的版本号有点用：它变了，说明对端重新生成了一份会话描述。

两百行里，只有八组属性真正影响连通

一份典型的 Chrome offer 有一百多行，去掉噪音后真正决定「能不能通、通成什么样」的只有这些。记住这八行，读 SDP 的速度会立刻上一个台阶。

属性它决定什么改错了的现象
a=ice-ufrag / a=ice-pwd这条传输的凭证对端不知道新的，检查全被拒，永远 failed
a=candidate一条可达地址少一条就少一条路；手写的多半是死的
a=fingerprintDTLS 证书指纹，用来绑身份与实际证书不符，握手失败，媒体全黑
a=setup谁发起 DTLS 握手（actpass / active / passive）两端都写 active，各等对方，握手卡住
a=mid这条 m= 在 BUNDLE 组里的名字与 group:BUNDLE 对不上，整组协商失败
a=sendrecv 等方向属性这条流谁发、谁收单向黑屏，而且常表现为「有画面但不动」
a=rtpmap / a=fmtp号码到编码的映射与参数不知道收到的是什么，或参数不符直接丢
a=rtcp-fb反馈能力：NACK、PLI、码率控制丢了不重传、糊了不请求关键帧

一个最小的例子，注意它有多短：

v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
s=-
t=0 0
a=group:BUNDLE 0 1

m=audio 9 UDP/TLS/RTP/SAVPF 111
c=IN IP4 0.0.0.0
a=mid:0
a=sendrecv
a=rtcp-mux
a=rtpmap:111 opus/48000/2
a=ice-ufrag:8hV2
a=ice-pwd:k9Qm3rTz1sLpXc
a=fingerprint:sha-256 4A:5E:1C:...
a=setup:actpass

m=video 9 UDP/TLS/RTP/SAVPF 96
c=IN IP4 0.0.0.0
a=mid:1
a=recvonly
a=rtcp-mux
a=rtpmap:96 VP8/90000

端口写 9，因为它在 offer 里没有意义——真正的端口要到 ICE 之后才有。a=recvonly 与 a=sendrecv 同时出现也不奇怪：方向是按流算的，不是按人算的。

为什么必须交换两次

RFC 3264 定义了 offer/answer 模型，核心是一条不对称规则：

offer 是「我能这样」，answer 是「那就这样」。answer 只能收窄，不能扩张。

—— 应答方不能新增 m= 段，不能启用 offer 没提到的载荷类型，不能把 sendonly 变成 sendrecv。

为什么这么死板？因为它保证了一件事：交换结束那一刻，两端对「谈成了什么」的理解必然一致。 否则 answer 可以塞进 offer 没有的东西，发起方还得再问一轮，协商永远不收敛。

「收窄」有两种形态：减少（offer 提三种编码，answer 挑一种）和拒绝。注意后者——拒绝一条流的方式是把端口写成 0，不是把它删掉。

setLocalDescription 不是「设个变量」

  • setLocalDescription() 之后才开始收集候选，不是 createOffer() 的时候。这解释了两类经典 bug：offer 发出去时里面还没有候选；以为删个 candidate 就能刷新，其实要重新协商。
  • setRemoteDescription() 会凭空造出 transceiver。 对方 offer 里有几条 m=，你这边就多几个 transceiver，方向由「对方写的」与「本地已有的」取交集。
  • 两者都改 signalingState，而它决定你下一步允许做什么。状态不对，方法直接抛 InvalidStateError，不会悄悄失败。

候选也不必等 SDP 齐了再发：Trickle ICE（RFC 8838）允许先发 SDP、候选边收边补，这是建立时间能压到亚秒的原因。ICE 本身是 RFC 8445，属于第 3 讲。

三个状态，两端各一台

JSEP 把协商压成一台只有三个状态的小机器。规范是 RFC 9429（2024-04 发布，废止 RFC 8829——网上大量教程还写着 8829）。

最该记住的是：have-local-offer 和 have-remote-offer 都是合法状态，不是卡死。 线上看到 signalingState 停在这两个值，说明你在等对面——多半是信令丢了，该查 WebSocket，不是查编解码。

glare：两个人同时开口

A 和 B 同时点了「开始共享屏幕」，两边同时 createOffer，这就是 glare。两边都进 have-local-offer，然后各自收到对方的 offer——此时调 setRemoteDescription(offer)，规范要求先做一次隐式回滚：撤掉本地那个还没被接受的 offer，退回 stable，再套用对方的。

但如果两边都回滚、都接受，就会互相顶掉、来回震荡。所以必须有一端「有礼」：有礼的回滚并接受，无礼的直接无视撞车的 offer。 前提是有一个两端能算出同样结果的确定性规则——通常是比较 peer id 字符串，谁小谁有礼。

// perfect negotiation 的骨架：只留判断逻辑，省略信令细节
let polite = false;   // 两端必须得出相反结论，规则要确定性
let makingOffer = false;
let ignoreOffer = false;

pc.onnegotiationneeded = async () => {
  try {
    makingOffer = true;
    await pc.setLocalDescription();        // 无参版：内部替你 createOffer
    signal.send(pc.localDescription);
  } finally {
    makingOffer = false;
  }
};

async function onDescription(description) {
  const collision = description.type === 'offer' &&
    (makingOffer || pc.signalingState !== 'stable');

  ignoreOffer = !polite && collision;
  if (ignoreOffer) return;                 // 无礼方：装作没看见

  await pc.setRemoteDescription(description);   // 有礼方：这里隐含 rollback
  if (description.type === 'offer') {
    await pc.setLocalDescription();        // 内部替你 createAnswer
    signal.send(pc.localDescription);
  }
}

这里最容易错的不是技术，是逻辑：两端算出同一个 polite 值。都 polite 就互相顶，都无礼就互相无视——后者的现场表现是「两边都显示正在连接，谁也连不上，日志一片安静」。

BUNDLE：三个 m=，一条传输

2000 年代的模型是一条流一条传输：音频一条、视频一条，各自做 ICE、各自握手、各占端口。放到 NAT 后面就是三次打洞、三个映射、三倍失败概率。

今天默认合并。a=group:BUNDLE 0 1 2 声明这三条归一组，每条 m= 用 a=mid 拿一个名字，整组共用一条传输。

代价是耦合：一条传输挂了，挂在上面的所有 m= 一起挂。 所以「音频好好的、视频没了」通常不是传输层的问题——传输层要挂就是全挂。a=rtcp-mux 则是另一层合并：RTCP 也走同一端口，一条流只占一个端口而不是两个，这个数字在 TURN 上是要花钱的。

为什么手改 SDP 几乎总是错的

「munge SDP」= 拿到 createOffer() 的结果，用字符串替换改几行，再喂给 setLocalDescription。它流行是因为历史上确实解决过问题，但有四种后果，一种比一种难查。

一、改动只在「这一次发出的字节」里生效。 浏览器以本地状态为准——transceiver 集合、sender 的 track、transport 的候选与密钥。下次 setLocalDescription 会从本地状态重新生成，你的改动全消失。现象于是变成「改了有用，过一会儿又不行」。

二、删 m= 行是单方面毁约。 合同里没有「这条不存在了」这种条款，要拒绝只能把端口写 0。整行删掉，对端拿到的是一份它没预期的合同——最好的情况是报错，最坏是按次序错位匹配。

三、调 m= 顺序会打乱 mid 绑定。 很多人为了让视频排前面，手工对调两段 m=，却没改 a=mid 和 group:BUNDLE。结果视频顶着 mid:0 的名字被塞进本该承载音频的传输上——ICE 说连接正常，媒体说不出话。

四、改方向等于替对端签字。 在 answer 里把 recvonly 改成 sendrecv，你写了「我要发」，但对方从没同意收；而本地 transceiver 还是 recvonly，本地也不发。合同上写着发，本地不发，谁都没错，就是没画面。

正确的做法只有一条：用 API 表达意图，让浏览器去写 SDP。 加流用 addTrack / addTransceiver，改方向改 transceiver.direction，换源用 sender.replaceTrack，限编码用 setCodecPreferences，调码率用 setParameters——需要协商时它们会自己触发协商。

方向：四态，以及「加了 track 没画面」

方向只有四个值，最常见的误解是它「谁写谁算」。实际是两端各写一边，取交集。

方向含义典型场景
sendrecv我发也收默认值，双向通话
sendonly只发不收推流、共享屏幕的主播端
recvonly只收不发观众、只看预览的坐席
inactive不发不收，但这条流还在临时关摄像头，不想重新协商

inactive 与 stop() 是两件事，混淆会造成不可逆故障：前者可逆，m=、mid、传输都还在，随时能改回来；后者把这条 transceiver 永久作废，m= 变成端口 0，之后再 addTrack 只会新建一条 m=，而新 m= 必须重新协商。

回到引子：direction = 'inactive' 没错，错在重新打开时只改了 track.enabled。三者区别值得单独记一行：

track.enabled = false                // 仍在发，发黑帧。不协商，对端仍"收到"
transceiver.direction = 'inactive'   // 不再发。要重新协商才生效
transceiver.stop()                   // 永久废弃这条 m=。不可逆

「我加了 track，对面还是没画面」，按这个顺序查，三步之内能定位：

  1. 看对端那条 m= 的方向。 answer 里若是 inactive 或 recvonly，问题不在你这儿——对方压根没打算收。
  2. 看本地 sender 有没有真绑上 track。 getSenders() 里逐个看 sender.track 是否为 null、track.readyState 是不是 live。设备被别处抢走时 track 会变 ended，页面毫无提示。
  3. 看有没有真的在发。 outbound-rtp 的 bytesSent 涨不涨——这一步能一刀切开「没发」与「发了但对面没收到」。

决策清单：什么时候必须重新协商

判断标准只有一句：这次改动是否改变了合同条款？ 改了就得重签，没改就不用。

  1. 改变流的数量或方向 → 必须重新协商。 加一路屏幕共享、把 sendrecv 改成 sendonly、恢复一条 inactive 的流，都是改条款。
  2. 只改编码参数 → 不需要。 码率上限、帧率、分辨率、请求关键帧，都走 setParameters()。合同一个字没改。
  3. 只换媒体源、不换类型 → 不需要。 replaceTrack() 换摄像头、从摄像头切到屏幕共享（都是 video），mid 与编码都不变。这是最被低估的一招。
  4. 换网络路径 → 需要 ICE restart，不是新协商。 m= 一条不加，但 ice-ufrag / ice-pwd 要换新，所以仍要走一遍 offer/answer。

反过来用还能得到一个判据：「通着通着不动了」先怀疑 ICE；「一开始就没通过」先怀疑方向。 两者的时间特征完全不同，而人往往一上来就怀疑编码。

可带走的判断力

第一，SDP 是结果，不是输入。 它是浏览器按本地状态生成的快照：读它为了诊断，写它为了闯祸。

第二，协商是两台状态机对齐，不是一次函数调用。 任何「卡住」先问「我这台在哪一态、对面那台在哪一态」，答案通常在信令层，不在媒体层。

第三，m= 的顺序和 mid 是绑定关系，不是排版。 记住这一点，你就不会去做「把视频调到前面」这种看起来无害的操作。

推荐一手资料： RFC 9429 — JSEP —— 不用通读。读两处就够：一是它对 SDP 语义的约束（哪些 a= 行必须被尊重、哪些组合非法），二是 setLocalDescription / setRemoteDescription 处理流程那一章——那里解释了为什么规范坚持让 JS 显式调这两个方法。
对照读 RFC 3264 — An Offer/Answer Model with SDP —— 重点读「Modifying the Session」那一章：重新协商时哪些能变、哪些必须保持，以及用端口 0 拒绝一条流的写法。这是「什么时候不需要协商」那张清单的法理来源。
状态机的最终依据在 W3C: WebRTC —— 现行推荐标准，2021-01-26 首发、2025-03-13 修订。查 signalingState 的定义、以及各方法在非法状态下抛什么异常，比任何博客可靠。
背景见 RFC 8825 第 3 节：信令被明确排除在标准之外——所以「SDP 怎么送到对面」永远是你自己的问题。
