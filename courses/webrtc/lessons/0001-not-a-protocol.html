深入 WebRTC · 第 1 讲

它不是协议，是一套强制约定

一句话目标：读完这一讲，你能说清 WebRTC 到底标准化了什么、故意没标准化什么，并从「三条约束」推出它为什么必须长成现在这个样子。

引子：两个标签页通了，手机不通

你在 VPS 上起了一个 mediasoup，本机开两个标签页互连——有声音，有画面，一切都对。第二天用手机 4G 再试，控制台只有一行：iceConnectionState: failed。你换了个 TURN 服务商，好了。你没改一行代码。

这件事值得停一下。它说明 WebRTC 的成败有一大半不取决于你写的代码，而取决于两端所处的网络愿不愿意让路。而它之所以这样设计，是因为它要解决的那三个约束，每一个都比「传输音视频」本身更硬。

三个约束，推出全部设计

约束一：两端互相不可见。 你在家里 192.168.1.20 后面，对面在公司 10.0.0.8 后面，中间隔着一到两层 NAT。两边都没有一个稳定、可寻址、能对外宣告的公共身份。这不是配置问题，是 IPv4 地址耗尽之后的常态。

约束二：没有共享的可信基础设施。 规范不能假设「你们公司有一台大家都信得过的服务器」。任何中间节点都可能是敌对的、被劫持的、或者干脆不存在。

约束三：实时。 延迟预算是几百毫秒，不是几秒。人对「对话」的容忍度极低：ITU-T 对会话式音频的单向延迟目标是 150 ms 以内、视频 200 ms 以内（换算成 RTT 约 300 / 400 ms）。超过这个量级，对话就会开始互相抢话。

把这三条分别翻译成设计决策，WebRTC 的形状就出来了：

约束设计回应代价
两端不可见ICE 自己找路 + 借信令传递信息连接建立慢、要探测、可能失败
无共享可信设施强制加密；用 SDP 里的证书指纹绑定身份握手多一个 RTT；密钥管理变复杂
实时UDP 承载 + 自己做拥塞控制 + 丢弃而非重传会丢帧、会糊、会自适应降质

这三条不是背景知识，是判据。后面每一讲遇到「为什么要这么麻烦」的时候，答案几乎都能回到这张表：要么是在对抗不可见，要么是在对抗不可信，要么是在对抗时间。

第一原则：迟到的包，等价于丢失的包

为什么不用 WebSocket 传音视频？WebSocket 是 TCP，而 TCP 的「可靠」在实时场景里是负资产。

TCP 保证有序交付。于是只要有一个包丢了，后面所有已经到达的包都必须压在接收缓冲区里等着——这就是队头阻塞（head-of-line blocking）。一次重传最短也要一个 RTT；如果链路开始丢包，TCP 还会同时收缩拥塞窗口，把发送速率也一起降下来。结果是：网络稍微抖一下，画面就停住，然后突然快进。这不是「稍微差一点」，而是从可用变成不可用。

视频本身对丢包是有容忍度的：丢一帧，画面糊一下、或者轻微卡顿 33 毫秒，人几乎察觉不到。但对延迟毫无容忍度：晚到 500 毫秒的一帧，在通话里就是废帧——它已经错过了该显示的时刻。

实时媒体的第一原则：迟到的包，等价于丢失的包。

—— 这句话能推出后面几乎所有机制：为什么用 UDP、为什么要抖动缓冲、为什么要 NACK 而不是重传、为什么要主动降码率。

所以 WebRTC 的做法是：换到 UDP，然后在应用层重新实现它真正需要的那部分可靠性。不是全量重传，而是选择性重传（NACK 只补关键包）、前向纠错（FEC 用冗余换延迟）、丢包隐藏（PLC 用算法猜）。这三样东西在第 6 讲会展开。

它没有发明协议，它规定了协议的组合方式

这是最容易误解的一点。WebRTC 不是一个新协议，RFC 8825 里它是「一组协议的用法」。找路用的是 2005 年就有的 ICE，加密用的是 DTLS-SRTP，传媒体用的是 RTP，传数据用的是 SCTP——全是别的工作组早就做完的东西。

把这条栈记住，排障顺序就自然出来了：先看有没有 UDP 通路，再看候选对有没有成功，再看 DTLS 有没有握上手，最后才轮到码率与画质。 绝大多数「音视频不通」的问题都死在前三层，但九成的调试时间被花在第四层。

真正新增的东西只有两样

一是一层 JavaScript API（RTCPeerConnection 等），让浏览器内部那套 C++ 实现变得可编程。二是一组「必须这样做」的强制约束——而这里最硬的其实是一堆禁止项。

RFC 8827 把话说得很直白：所有媒体通道必须经 SRTP/SRTCP 保护，禁止明文 RTP；必须为每个媒体通道提供 DTLS-SRTP；禁止使用 SDP security descriptions（SDES，即把密钥直接写在 SDP 里）；禁止协商 NULL 加密；禁止实现 DTLS 重协商与 TLS False Start。此外，每次通话都要生成新的密钥对（不可链接性），不同 origin 使用不同密钥对。

为什么禁得这么狠？因为这些约束的服务对象不是「开发者」，而是「不小心的开发者」和「他遇到的攻击者」。一条链路只要允许「为了省事走明文」，就一定会有人在生产环境走明文。所以规范干脆把省事的路堵死。

控制面与数据面被彻底切开

RFC 8825 第 3 节把「客户端到服务器的信令怎么走」明确列为不在本协议族范围内。这不是偷懒，是刻意的：不同应用要用不同的信令（SIP、XMPP、WebSocket、或者你自己发明的任何东西），硬要标准化只会变成谁都不满意。

于是有了 WebRTC 最反直觉的一条：RTCPeerConnection 不知道对方在哪里，也不负责把任何东西送到对方那里。 它只负责两件事——把「我支持什么、我怎么被联系到」写进 SDP，以及在你把对方的 SDP 喂进来之后，照着去做。

// 协商 = 你自己搬运 SDP。浏览器不负责送达。
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);   // 这一刻才开始收集候选地址
signal.send(JSON.stringify(pc.localDescription));

// 对端
await pc.setRemoteDescription(offer);
await pc.setLocalDescription(await pc.createAnswer());
signal.send(JSON.stringify(pc.localDescription));

看到那个注释了吗——候选地址是在 setLocalDescription 之后才开始收集的，不是 createOffer 的时候。这一个细节解释了两类常见 bug：一是「offer 发出去时 SDP 里还没有候选」，二是「以为改了 candidate 就能刷新，其实要重新协商」。

这个空白一直存在到 2025 年 3 月——RFC 9725（WHIP） 才为「推流到媒体服务器」这一个特定场景补上了标准化的 HTTP 信令：一次 POST 换 SDP，然后用 PATCH 补 ICE。但它只覆盖推流，不覆盖通话。

「P2P」是目标，不是保证

WebRTC 的名字让人以为它总能点对点。事实是：直连是它优先尝试的路径，不是它承诺的结果。 这一点藏在 ICE 的候选优先级里：host 类型建议 126、server-reflexive（公网映射）100、relay（中继）0。中继不是 1，是 0——只有当所有优先级更高的配对都探测失败，中继才会被选中。

但优先级低不等于罕见。callstats.io 对上百个 WebRTC 服务的观测（2015-01 至 2016-02，数十亿分钟）显示：22% 的会议需要某种形式的 TURN 中继，9% 需要 TCP；而会话建立失败率是 12%，这些失败里 85% 来自无法穿透 NAT / 防火墙。注意年份——它只能当量级用，别当成今天的精确值，更别直接写进商业计划。但它足够支撑一个工程判断：中继是常态成本，不是边缘情况。

还有一层更现实的变化：今天大多数产品根本不点对点。客户端把媒体发给服务端的 SFU（选择性转发单元），由它转发给其他人。这时候「P2P」这个词已经名不副实——你的对端是一台有公网地址的服务器，NAT 问题因此大幅简化。第 8 讲会专门算这笔账。

这条线要走到哪里

后面七讲是一条单向的路，每一讲都在回答上一讲留下的问题：

  1. 协商——SDP 与 offer/answer：为什么它是状态机而不是配置表，为什么「改 SDP」是个危险动作（第 2 讲）。
  2. 连通——ICE 的候选、检查与提名：那个 failed 到底卡在哪一步（第 3 讲）。
  3. 穿越——NAT 的真实行为：为什么「四种 NAT 类型」这个流行说法是过时的，以及中继成本怎么估（第 4 讲）。
  4. 加密——DTLS-SRTP：为什么信令服务器看得到 SDP 却看不到你的画面（第 5 讲）。
  5. 容错——RTP 打包、NACK、抖动缓冲：丢包之后到底发生了什么（第 6 讲）。
  6. 自适应——拥塞控制：为什么「糊一下」是算法主动做出的选择（第 7 讲）。
  7. 决策——拓扑、容量、可观测性：上线前该检查什么（第 8 讲）。
