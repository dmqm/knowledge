# Mission: 深入 WebRTC

## Why

我在自己的机器和 VPS 上折腾自托管服务（NAS、Docker、Tailscale），现在想再往前走一步：**能自己搭一条实时音视频链路，并且在它出问题时能自己定位**，而不是照着教程抄一段代码、跑不通就换一个库。WebRTC 的坑几乎都不在 API 上——它在 NAT、协商、加密与拥塞控制这四层里。把机制吃透，意味着我能判断「这个库为什么这样设计」「这次为什么走了中继」「画面糊是算法的选择还是配置的错」。

## Success looks like

- 拿到一份真实 SDP，能逐行读出媒体方向、编解码、ICE 参数与证书指纹，并说清哪几行改了会导致连不上
- 能解释一次连接**为什么**走了 TURN 中继，并给出中继带宽与费用的量级估算
- 面对「连不上 / 听不清 / 画面糊」三类故障，能按 candidate → ICE → DTLS → RTP/拥塞 的次序分层定位，并用 `getStats()` 给出证据而不是猜
- 能对一个具体场景（1 对 1、多人会议、直播分发）选出 P2P / SFU / 转协议链路，并说清上行带宽与成本的假设
- 能在本机跑通一个最小可用的服务端实现（Pion 或 mediasoup 或 LiveKit），并接入自己的前端页面

## Constraints

- 手机端优先阅读：讲义要能随时打开、随时读完一讲，但**深度优先**——要机制、真实案例与决策链，不要概念清单
- 已有后端 / 运维背景，但**没有**音视频领域经验；不回避协议细节，也不假设我读过 RFC
- 所有页面离线可用、零外部依赖；图一律内联 SVG，不加载任何 CDN
- 事实纪律：具体数字与规范结论一律挂一手出处（RFC / W3C / 公开测量），不编数字、不编引文
- 环境：Windows 本机 + Docker；公网服务用一台 VPS，不是云厂商全家桶

## Out of scope

- 视频编码标准内部原理（H.264 / AV1 的变换、量化、码率控制细节）——只需要知道它对上层意味着什么
- 完整 SIP / VoIP 电话栈，以及与运营商网络的互通
- 前端 UI 与设计系统（按钮、布局、动效）
- 大规模压测与容量自动扩缩容的实现细节（本课只给量级估算方法与公式）
