第 1 讲 · 它不是协议 概念速查表

深入 WebRTC · 速查表

排障阶梯

按协议栈自下而上定位。核心纪律：每一层都必须拿到证据再往上走，不要因为「看起来像网络问题」就跳到改码率。

为什么是阶梯，不是流程图

WebRTC 的故障有一个强特性：下层不通，上层一定没有信号。所以从下往上查，每一步只有两种结果——通过，或者就在这里停住。反过来从上往下查（先看画质、先调编码）会在下层已经断掉的情况下得到一堆无意义的指标，然后误判。

这跟排查网络问题的方式完全一致：先确认 L1/L2 通不通，再看路由，最后才看应用。你已有的运维直觉可以直接迁移。

第 0 层：前置条件

检查项为什么
页面在 HTTPS（或 localhost）下否则 getUserMedia 直接被拒，连媒体都没有
getUserMedia 的权限已授予失败率里约 14% 归因于采集，其中过半是用户拒绝授权
设备没有被其它程序独占会议软件、录屏工具会锁摄像头，表现为 track ended
两端时钟无异常极端情况会影响 DTLS 证书校验与日志对齐

第 1 层：候选收集

看哪里：pc.onicecandidate 收到的候选类型；或 chrome://webrtc-internals 里的 icecandidate 事件列表。

现象判断动作
只有 host，没有 srflxSTUN 没配或不可达检查 iceServers 配置与 STUN 可达性（dig/curl 同一网络）
只有 host 与 srflx，没有 relayTURN 未生效检查 TURN 凭据（临时凭据过期是最常见原因），以及 TURN 的 3478/443 是否可达
完全没有候选配置被完全忽略确认 iceServers 写在构造参数里、且没被后续 setConfiguration 覆盖
候选很多但连接慢候选过多拖慢收敛减少网卡类型（如关闭 IPv6 或虚拟网卡），收敛反而更快

第 2 层：ICE 连通性

看哪里：pc.iceConnectionState 与 pc.getStats() 里的 candidate-pair（尤其 state 为 succeeded 且 nominated 的那一对）。

现象判断动作
卡在 checking 不前进探测发了但没有回包看是否有 relay 候选；查对端是否收到候选（Trickle 通道是否实现）
直接 failed所有配对都失败UDP 被封或两侧 NAT 都不配合；上 TURN over TCP/TLS 443
connected 但很快 disconnected路径失效映射超时或切网；启动 ICE restart，而不是重建 PeerConnection
选中了 relay，但你希望直连直连配对失败这是结论不是故障；若要优化，查 STUN 是否可用、NAT 是否对称

第 3 层：安全握手

看哪里：pc.connectionState（含 DTLS）与 pc.getStats() 里的 transport 的 dtlsState。

关键区分：iceConnectionState === 'connected' 但 connectionState 仍不是 connected，说明路通了，但对面不认你。

现象判断动作
DTLS 一直不完成证书指纹不匹配，或 SDP 被中间环节改过核对两端 SDP 里的 a=fingerprint 是否与被改写的信令一致；禁止中间层重写 SDP
偶发握手失败大包被丢（MTU / 分片）检查 tunnel / VPN 的 MTU；确认没有设备丢弃分片 UDP
a=setup 冲突两侧都要求做主动方不要手写 setup；让 offer 端用 actpass

第 4 层：媒体与质量

看哪里：inbound-rtp / outbound-rtp / remote-inbound-rtp。

指标含义怎么用
packetsLost / fractionLost丢包数与丢包率结合 RTT 判断是无线干扰还是链路拥塞
jitter到达间隔抖动抖动高但丢包低 → 缓冲与调度问题，不是带宽问题
currentRoundTripTime候选对 RTT中继路径会明显高于直连；用它验证「是不是绕路了」
availableOutgoingBitrate估计可用上行长期低于你设的 maxBitrate → 瓶颈在网络
qualityLimitationReason编码受限原因bandwidth / cpu / none / other，一步分开三种病因
freezeCount卡顿次数比「平均帧率」更接近用户体感
frameWidth / frameHeight实际编码分辨率降分辨率是算法的主动选择，用它确认「糊」到什么程度

五个典型画像

  1. 「我家能用，客户公司不能用」——第 2 层。企业网封 UDP 或强制代理。处方：TURN over TCP/TLS 443，并确认 TURN 域名可达。
  2. 「两个人在同一个办公室反而连不上」——第 2 层。hairpinning 失败。处方：允许走 relay，或让 SFU 兜底。
  3. 「连上了但完全没画面，也没声音」——第 3 层或方向协商。先看 connectionState，再看 SDP 的 direction 是否为 inactive。
  4. 「画面糊，声音正常」——第 4 层。看 qualityLimitationReason：bandwidth 就降码率/换层，cpu 就降分辨率/换硬件编码。
  5. 「声音断续，视频正常」——不是拥塞。查音频采集设备被抢占（蓝牙耳机）、系统采样率、或抖动缓冲异常。

三条通用纪律

一、先记录再动手。 复现时立刻存一份 getStats() 快照与 chrome://webrtc-internals 的导出（它能把整条会话的曲线存下来）。事后靠记忆复盘几乎一定错。

二、一次只改一个变量。 WebRTC 的故障链很长，同时改三处会让你失去因果判断——尤其是「加了个 TURN 就好了」这种结论，很容易掩盖真正的原因（比如其实只是 STUN 域名解析失败）。

三、区分「失败」与「降级」。 走了中继、码率降到 300 kbps、分辨率降到 360p——这些多数是系统在正常工作，不是 bug。真正要修的是「为什么必须降级」，而不是把降级逻辑关掉。
