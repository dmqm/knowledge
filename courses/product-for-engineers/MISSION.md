# Mission: 工程师的产品思维

## Why
我是一名后端开发 / 架构师。技术能力越强，越容易发现一个尴尬的事实：**把系统做对（正确、可扩展、无 bug）和把对的东西做出来（有人真正需要、值得投入）是两种不同的能力**。我想补上后者——不转岗做产品经理，而是在自己的工作里多一层"该不该做、值不值得做"的判断力，从而少做无效的功、更早发现方向错误。

## Success looks like
- 拿到一个需求时，能先问出"用户要完成的到底是什么任务"，而不是直接进入方案设计
- 能对一个功能做一次粗略的机会评估（价值 / 成本 / 风险），并说清结论是怎么来的
- 能用最小成本设计一次验证，而不是先写三个月代码再交给用户评判
- 在需求评审里，能把技术约束翻译成产品语言，和产品经理在同一张桌子上对话
- 能独立主导一个小产品，从问题定义一路走到上线后的迭代决策

## Constraints
- 手机端优先，讲义短、随时可读；但**深度优先**——要机制、案例与决策链条，不要概念清单
- 后端 / 架构背景，避免"手把手教画原型 / 教 Axure"这类设计工具课
- 每讲落到一个具体、真实的案例，避免纯理论
- 事实纪律：不编数字、不编引文，具体断言一律挂一手出处

## Out of scope
- UI / 交互设计工具与视觉设计技能（Figma、Axure 等）
- 完整的产品经理职业转型路径与求职
- 增长 / 运营 / 市场投放的执行细节
- 与"判断该做什么"无关的项目管理流程（如排期工具、Scrum 仪式）
