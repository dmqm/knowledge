工程师的产品思维 · 第 3 讲

这件事，值不值得做

一句话目标：读完这一讲，你能在拿到一个机会的十几分钟里，用「价值 / 成本 / 风险」三问把它摆到一个 2×2 上，给出「做 / 塑形后再做 / 不做」的初步结论，并说清结论是怎么来的。

引子：需求池里同时躺着两个东西

需求池里通常同时躺着两个东西。A 是一套高级权限规则引擎——难、优雅、能进架构图，还能写进季度汇报，客户里最挑的那几家一直在提。B 是「在任务列表里一眼看出这条任务被谁卡住了」——不起眼，甚至没人正式提过，但客服工单里反复出现「找不到」「得一个个点开看是谁没交」。

当你被问到「这两个能不能做」，答案都是能。于是你按直觉把 A 排在了前面——因为它更难、更酷，做完更能证明工程能力。

这一讲要给你的，正是一把能在动手之前就摆平这类问题的尺子。它给出的结论往往是反直觉的：B 大概率该先做，而 A 可能根本不该做。

「能不能做」是个不完整的问题

工程训练把「能不能做」问到了极致：给定一个需求，能不能实现、要多复杂、有哪些边界情况、扛不扛得住量。这个问题的答案极重要——但它只回答了一半。另一半是「值不值得做」。

「能」和「值」是两条独立的轴。 一件事完全可能技术上轻松却毫无价值，也可能价值巨大但用错了方式去做。工程思维默认只优化前者，于是系统性地产生一个偏差：越难做、越能展示能力的方案，越容易被选中。 而恰恰是这类方案，最可能昂贵却只服务少数人。

更隐蔽的一层是沉没动力。一旦你开始认真想「怎么做」，脑子里的方案会越长越完整——异步队列怎么拆、表怎么设计、边界怎么兜。方案越完整，越难放弃。工程能力强的人，这个偏差反而更大，因为他能更快、更完整地构建出「可做」的图景，而那幅图景本身就会替他做决定。

所以第一句要记住的是：可行性得到确认，不等于价值得到确认。 先回答「能不能」，再回头问「值不值」；顺序一旦反了，判断就已经被方案绑架。

三问：价值、成本、风险

把「值不值得做」拆成三个能分别回答的问题，就是一套粗略但可执行的评估。注意「粗略」是刻意的：你手上的信息本来就不多，做成精确到小数点的评估只会带来虚假的确定感。三问的目标不是预测未来，而是排序与淘汰。

第一问：价值——谁、多痛、多频繁

价值不是一种感觉，至少可以拆成三个维度相乘：

  • 触达多少人（reach）——它影响多少用户？是全部核心用户，还是一小撮？
  • 有多痛——不做会怎样？是「有点想要」，还是「卡住任务、只能绕路」？
  • 多频繁——每天发生，还是每年一次？

任何一个维度接近零，乘积就接近零。但关键是别用单一维度一刀切：一个只服务三家大客户的高权限功能，触达是小，可如果这三家每天用、痛点致命，价值未必低；反过来，「很多人偶尔遇到的一点小烦」也可能因为频率低，不配一次大投入。三个维度要一起看，而不是抓住其中一个下判断。

第二问：成本——要的是量级，不是工时

工程的本能是估算：先想清怎么做，再得出一个数。《Shape Up》 把它概括得很准——估算从一个设计出发，得到一个数字。

产品判断要把它反过来：先给一个数字，再让设计去迁就它。 这就是 Shape Up 的 时间预算（appetite）：不问「这件事要花多久」，而是问「我愿意为它花多久」。这个先后顺序的调换，是整个方法的核心。

为什么有效？因为「再做一点会更好」永远成立，项目只要没有边界就会一直膨胀。时间预算提供的是固定时间、可变范围（fixed time, variable scope）：deadline 是固定的，范围是可以砍的，质量不能降。 于是取舍变成一个必须做的动作——哪些是核心、哪些是边缘，你被迫想清楚。Shape Up 把预算设成两档：Small Batch（一两个人一两周）与 Big Batch（同样规模的团队六周）。

用工程语言说：你早就习惯了「容量规划」——给定 QPS 上限，再去设计架构。时间预算就是先给这件事划一条「资源上限」，再在限额内设计方案。它约束的不是「做多快」，而是「做多小」。

第三问：风险——哪条假设最可能错

一件事值不值，最终取决于一串假设是否成立：用户真需要、用户会用、用户会因此改变行为、业务算得过账。产品里最贵的往往不是「实现错了」，而是「假设错了」。 假设错了，做得越好、投得越多，浪费越大。

所以第三问不是泛泛地问「有什么风险」，而是更锋利的那一刀：哪一条假设如果错了，代价最大？ 那才是最危险的假设，验证要从它开始，而不是从最容易验证的那条开始。

Cagan 的四问：你其实只负责其中一格

Marty Cagan 把一个机会要过的关卡总结成四问（出自 《INSPIRED》）：

  • 可行性（feasibility）：技术做得到吗——工程负责；
  • 可用性（usability）：用户用得明白吗——设计负责；
  • 价值（value）：用户真的需要吗；
  • 商业可行性（viability）：业务算得过账吗。

这四问和刚才的三问是同一件事的两种切法：价值这一问覆盖了 value 与 viability，成本与风险横跨 feasibility 和其余各格。

这里有一条对技术人特别重要的提醒：你天生只会认领第一格。 「可行性」是你的主场——你的职业训练、你的自豪感、你和同事的共同语言，全在这一格里。但四问里出问题最多的，从来不是「做不做得到」，而是「用户到底需不需要」。如果你只回答可行性，你就把四分之三的判断留给了别人，而且往往是留给了没有条件回答它们的人。

真实案例：Basecamp 的「日历」

再看一个真实到可以照着抄的例子，出自 Ryan Singer 的 《Shape Up》（Basecamp，全文免费在线）。

Basecamp 发布第三版时没有日历功能，只有一个把事件一条条列出来的 schedule 视图。上线后，客户开始要求「加个日历」。

按「能不能做」，这题根本不用想：能，而且团队以前做过日历，知道它有多复杂——一本正经的日历，六个月以上都不一定够。

但价值这一问立刻变了味道：过去版本的 Basecamp 有日历，可只有大约 10% 的客户用。 于是他们不肯为它花六个月。反过来说，如果有什么能在一个六周周期内满足写信来的那批人，他们愿意试。

六周只能做出「人们说日历时所想内容的十分之一」。问题于是从「能不能做日历」变成了「做哪十分之一」。 他们去调研了一位提需求的客户，不问「你想要什么样的日历」，而是问「你什么时候想要日历、当时在做什么」。答案很具体：她办公室墙上画着一个大日历，同事们在上面标会议室的占用。有一天她在家办公，客户来电要排会，她只能开车回办公室看墙上的日历——路上堵车，最后还没找到合适的空档。如果她能从家里的电脑上看到哪些时段是空的，就能省下一小时车程和一大堆挫败。

洞察不是「把日历搬到电脑上」（那太显然了），而是：真正重要的是看见空档。他们把需求从「做日历所能做的一切」，收窄成「帮我看见空档，好决定什么时候排会」。方案随之变成一个两个月、只读的网格：有事件的日子画个点，点某天就把当天的事件滚动到眼前——他们叫它 Dot Grid。

关键是团队明确写下了不做的部分：不能拖动事件换天、不做跨天事件、不做颜色分类。这些取舍不是偷懒，而是基于对用例的理解——正因为理解了「看见空档」这个核心，才敢砍掉其余。

用本讲的三问回看，这件事的落点清清楚楚：

三问全功能日历看见空档（Dot Grid）
价值 过去只有约 10% 客户用过，触达小 排会与资源安排的核心路径，卡住的是多数人的日常
成本 六个月以上 被塑形进六周预算
风险 做完六个月才知道没人用 假设是「看见空档」就够用，能在周期内被验证

Shape Up 里还有一例，更能说明「成本量级是可以被重塑的」：有客户要求更复杂的权限规则，做出来可能花六周。团队没有照单全收，而是深挖背景，发现真正发生的是——有人归档了一个文件，却不知道这会让所有人都看不见它。 于是他们不去做权限规则，而是在归档动作上加了一句警告，说明影响。从六周的项目，变成一天的改动。

这两件事的工程含义是同一个：先问需求背后的量级与价值，再决定投什么规模的工程。 不是「日历难做所以放弃」，而是「只有约 10% 的人用过，不配六个月」；不是「权限规则做起来麻烦」，而是「六周的成本，配不上一个本可以用一句警告解决的问题」。

三个坑

  1. 把时间预算当成「拍脑袋压工期」。 时间预算不是「我们想快点」，它是一个创造性约束——逼你重新设计问题，而不是把同样的范围硬塞进更短的时间。范围不变、只压进度，那叫欠下产品债。
  2. 把价值估计当成精确预测。 三问产出的是量级和相对排序，用来决定先做谁、谁不做。它不负责给出精确数字；精确留给后面的验证。
  3. 把「不做」当成失败。 评估的价值有一半在于决定不做什么。能说清「这件事为什么不做」，本身就是替团队省下最贵的资源——时间。

一次十五分钟的评估

下次有人把功能请求放到你面前，先不写代码，按这个顺序走一遍：

  1. 写下它要改变的结果。 不是「加个导出」，而是「谁因此能做什么」——动词 + 谁 + 变快 / 变少 / 变多。
  2. 价值：谁受影响、多痛、多频繁——各给一个量级（全部 / 多数 / 少数，致命 / 难受 / 想要，每天 / 每月 / 罕见）。
  3. 成本：给它一个时间预算，而不是估算。问「我愿意为它花一天、一周，还是一个六周周期」。
  4. 风险：列出假设，圈出最危险的那条——错了代价最大的。
  5. 结论：做 / 塑形后再做 / 不做——写下来，附上理由。

走完这五步，你依然不是产品经理，但你已经把「能不能做」补成了「值不值得做」，并给出一个能被别人反驳、能被证据推翻的判断——这才是判断力，而不是感觉。下一讲接着处理第三问：最危险的假设，怎么用最小成本先验证掉，而不是写完三个月代码再交给用户评判。

小练习

拿你手上最近一个功能请求（真的那个，别用假设的），在纸上或文档里写下三行：

（1）价值：它影响谁、多痛、多频繁？各给一个量级。
（2）成本量级：你愿意为它花多少时间？这个预算下，范围该砍掉哪几块？
（3）最危险的假设：哪条假设错了代价最大？你打算怎么验证它？

写完后，用上面的 2×2 把它摆一个位置。第 4 讲会接着用这张纸。

回顾：三问与摆位

点选项，立刻看解析

1. 在「能不能做」之外，产品判断还必须补上哪一问？

2. Shape Up 的「时间预算（appetite）」与估算的根本区别是什么？

3. Basecamp 最终没做「全功能日历」，核心理由是什么？

哪里没说清？回头直接问你的老师（那个正在运行本工作区的 agent）。它知道你的目标，可以就任何一句追问下去、举更多例子。

推荐一手资料： 《Shape Up》— Ryan Singer（Basecamp，全文免费在线） —— 本讲的「时间预算 / appetite」「固定时间、可变范围」以及 Basecamp 的日历案例都出自这里，第 3 章 Set Boundaries 讲得最透；读完你会明白「先给数字、再给设计」为什么能挡住项目无限膨胀。
