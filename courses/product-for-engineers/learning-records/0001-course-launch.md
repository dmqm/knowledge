# 0001 · 创建课程「工程师的产品思维」

- 状态：已接受
- 日期：2026-10-16

## 背景

学习者是一位**后端开发 / 架构师**。他的诉求是「学习基本的产品技能，补齐判断『该做什么』的能力」，而不是转岗做产品经理。他曾明确表示不喜欢浅尝辄止的材料（原话大意：「太浅了……这是一本书啊」），因此本课程定位为**深度优先**。

他最初的请求是「推荐一门产品课程」。但现有 `courses/` 里没有产品主题，而本仓库的约定是：课程内容由 agent 用 `teach` 技能生成，而不是推荐外部网课。于是决定**直接在 `courses/product-for-engineers/` 下新建一门课**。

## 决策

1. **主题定位**：不是「转行做产品」，而是「让工程师具备产品判断力」。范围只保留最能迁移到工程背景的部分，明确排除 Figma/Axure 等设计工具、求职、增长运营、无关的项目管理流程。
2. **结构**：6 讲，按「先改变视角 → 再给工具」推进：
   - 0001 「做对的事」vs「把事做对」（工程思维 vs 产品思维、交付陷阱）
   - 0002 用户说的，不是用户要的（需求 vs JTBD）
   - 0003 这件事，值不值得做（价值/成本/风险、时间预算、Cagan 四问）
   - 0004 先验证，再开发（最危险的假设、MVP、Build-Measure-Learn）
   - 0005 资源有限，先做什么（RICE、Kano、Effort 估计）
   - 0006 和产品一起，把事做成（把否决换成菜单、一页纸提案、主导自己的产品）
3. **形态**：手机优先的自包含 HTML 讲义，配 `reference/0001-glossary.html` 全课程共用术语表；每讲含一张内联 SVG 图示、一个真实案例（挂一手出处）、小练习与 3 题交互测验。
4. **事实纪律**：不编造数字、人名、引文；所有引用限 `RESOURCES.md` 中已验证的一手来源。
5. **生成方式**：第 1 讲作为格式与措辞基准单独手写；第 2–6 讲由子 agent 并行生成，要求逐字复用第 1 讲的结构、class 与测验脚本。

## 结果与影响

- 交付 6 讲正文（约 3000–5000 字/讲）、术语表、使命、笔记、资料清单。
- 校验通过：每讲 3 题测验、正确项位置打散、测验脚本与第 1 讲逐字一致、无写死颜色、标签平衡、所用 class 均存在于 `assets/style.css`。
- 术语表成为全课程**规范性措辞来源**；后续新增讲义必须与之一致。
- 已知缺口（记录在 `RESOURCES.md`）：中文一手资料偏弱，面向技术人的对口材料稀缺。

## 待办 / 可能的下一步
